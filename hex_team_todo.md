# Подробный TODO по проекту Hex.Team

Основано на внутреннем ТЗ команды по проекту **Java + Vaadin P2P LAN Communication**: локальный Spring Boot + Vaadin на каждом устройстве, discovery в LAN, signaling между backend-узлами, WebRTC для чата/файлов/аудио, локальное хранение, логи, метрики, безопасность, demo-ready архитектура и отдельное описание multihop..

---

# Как читать этот TODO

Этот TODO сделан не как список фич, а как **порядок реальной работы** для команды, которая хочет не просто “написать что-то”, а **собрать устойчивую базу**, на которую потом без боли навешиваются чат, звонки, файлы, безопасность и демонстрация.

Весь план разбит на 3 слоя:

1. **Фундамент** — база проекта. Это не MVP и не “минимум для показа”, а именно та основа, без которой дальше начнётся хаос.
2. **Основные блоки** — обязательный функционал из ТЗ.
3. **Опциональные блоки** — улучшения и stretch-функции, которые имеет смысл делать только после стабилизации основы.

У каждого блока ниже есть:
- цель;
- конкретные задачи;
- что считается результатом;
- что нельзя откладывать;
- что можно упростить.

# Блок 0. ФУНДАМЕНТ

## Зачем он нужен

Это самая важная часть. Её задача — подготовить **рабочий каркас узла**, в котором:
- всё запускается одинаково на каждом ноутбуке;
- есть понятная структура проекта;
- есть базовые доменные сущности;
- есть скелет discovery/signaling/session lifecycle;
- есть мост между Java и браузером;
- есть локальное хранилище;
- есть логирование и точки диагностики.

Если сделать этот блок качественно, все следующие фичи будут просто “вставляться” в готовые места. Если пропустить его и сразу пойти писать чат/звонки/файлы, проект начнёт рассыпаться на несвязанные куски.

## 1.4. Сделать передачу файлов

### Что сделать

1. Ввести `FILE_OFFER`, `FILE_ACCEPT`, `FILE_DECLINE`.

3. Резать файл на чанки.
4. Отправлять чанки по порядку.

6. Писать во временный файл на принимающей стороне.

### Минимум для первой рабочей версии

### Готово, если

- можно отправить файл;
- получатель принимает файл;
- прогресс виден;
- после получения проверяется hash;
- файл сохраняется локально.

3. На каждом чанке обновлять manifest.
4. При разрыве помечать transfer как `INTERRUPTED`.

### Зачем

Даже если полноценный resume не успеете, это уже даёт честную архитектурную базу под возобновление передачи.

### Готово, если

- при обрыве есть сохранённый temp-файл и manifest;
- система знает, что уже было получено.

# Итог

Главная мысль такая:

Сначала вы делаете **не “фичи”, а систему**, в которой есть:
- понятный узел;
- понятная идентичность;
- discovery;
- signaling;
- session lifecycle;
- JS bridge;
- хранение;
- логирование;
- UI-каркас.

Это и есть **фундамент**.

После него основная разработка превращается в последовательное добавление:
1. чата;
2. аудио;
3. файлов;
4. надёжности;
5. безопасности;
6. метрик и документации.

И только потом — resume, multihop code, видео и полировка.

Если держаться этого порядка, проект будет намного легче собирать и защищать.
